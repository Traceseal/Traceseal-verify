# traceseal-verify

Verify [Traceseal Execution Receipts](https://traceseal.io/spec): signed,
tamper-evident records of what an AI agent did, attested by its operator.

## What is an Execution Receipt?

A Traceseal Execution Receipt is a signed JSON document in which the
**operator** attests to:

- **What code ran:** a manifest hash over the source files;
- **Which publisher it came from:** the publisher fingerprint the operator recorded;
- **What sandbox it ran in:** a hash of the sandbox configuration;
- **What it produced:** SHA-256 of inputs and outputs (hashes, not values);

and signs all of it with the operator's Ed25519 key.

**What this verifier checks:** the operator's signature, that the displayed
operator identity is derived from the signing key, and, across several
receipts, gaps, forks, broken links and key changes not made through a
dual-signed rotation.

**What it does not check:** publisher signatures or transparency-log
entries (the printed `publisher:` line is what the operator recorded), that
the sandbox was actually enforced, missing receipts after the last one you
give it (that needs a checkpoint held by someone other than the operator),
or whether the operator's key is the one you should trust. A receipt is an
attestation by its signer, not proof that the signer was honest. See
[RECEIPT-SPEC.md](RECEIPT-SPEC.md) §5–6 and the
[legal notice](https://github.com/Traceseal/traceseal-observe/blob/main/LEGAL.md).

Third parties verify receipts with one command, without access to the
operator's machines.

## Install

```bash
pip install traceseal-verify
```

## Verify a receipt

```bash
traceseal-verify receipt.json
```

```
[OK] receipt.json
  skill:     agentmail v1.2.0
  operator:  ed25519:f19bc125dcfdb2eb91e98da98d45bb7a
  publisher: ed25519:a07c7eb5f20f6b99d1914d7ec5221a25
```

Every receipt type in the v1 envelope verifies: skill, model, tool,
data_flow, orchestration, outcome, oversight, policy_decision, incident,
erasure, evidence_pack, chain_key_rotation and the model-provenance
profiles. The output names the type and a few key facts:

```
[OK] receipts/02-oversight.json
  type:      oversight (decision=approved, review_seconds=30, chain=support-agent#2, agent=support-bot, reviewer_signed=true)
  operator:  ed25519:56475aa75463474c0285df5dbf2bcab7
```

## Verify a chain of receipts

Give several chained receipts at once and traceseal-verify also checks
the hash links between them:

```bash
traceseal-verify receipts/*.json
```

```
[FAIL] chain support-agent: seq 1..42, 40 receipt(s), from genesis: True
  GAP: seq 17..18 missing
```

It reports, across the receipts you supply:
- missing positions between them (gaps; a missing tail needs a checkpoint);
- two different receipts at one position (forks);
- broken `chain_prev_hash` links;
- signing-key changes that didn't go through a valid, dual-signed
  `chain_key_rotation`, including a key change across a gap.

Use `--allow-gaps` to report gaps without failing, and `--no-chain` to
skip these checks.

Checkpoints, inclusion proofs, RFC 3161 timestamps, time windows,
causality and human-oversight checks live in
[`traceseal-observe`](https://github.com/traceseal/traceseal-observe)
(`traceseal-chain`, `traceseal-trace`, `traceseal-report`).

## Python API

```python
from traceseal_verify import verify_receipt_file, check_chains

result = verify_receipt_file("receipt.json")
if result.ok:
    print(result.receipt_type, result.summary, result.operator_fingerprint)
```

## What verification checks

1. **Structure**: required sections present, recognised version.
2. **Consistency**: for skill receipts, execution and provenance agree on
   which code was signed.
3. **Fingerprint**: the displayed `operator_fingerprint` is derived from
   the embedded public key (spec §4 Step 3). It sits outside the
   signature, so without this check a valid receipt could be relabelled
   with someone else's identity.
4. **Signature**: the operator's Ed25519 signature is valid over the
   execution and provenance data.
5. **Chain links**: across multiple receipts, as above.

## What verification does NOT check

- Whether the operator's key is trusted. That's your policy decision. An
  organisation can publish its keys at
  `https://<domain>/.well-known/traceseal/operator-keys.json`; check them
  with `traceseal-keys verify` from traceseal-observe.
- Whether the publisher's key is trusted (your policy decision).
- Whether specific inputs or outputs match expected values (your
  application logic).
- Domain-profile semantics beyond the envelope, such as signed-time
  profile 1.1 rules. Those are checked by the profile's own tools.

## Generating receipts

Receipts are generated by [traceseal-observe](https://github.com/traceseal/traceseal-observe) (AI agent actions) and [Traceseal](https://traceseal.io) (sandboxed skills). This package is the verification side only, kept deliberately minimal (one dependency) so anyone can verify without installing the full toolchain.
