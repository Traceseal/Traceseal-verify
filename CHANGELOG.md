# Changelog

All notable changes to `traceseal-verify` are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Security
- **The operator fingerprint is now derived from the public key and
  compared** (RECEIPT-SPEC.md §4 Step 3). Previously the displayed
  `operator_fingerprint` was taken from the receipt as given. It is
  outside the signed payload, so a valid receipt could be relabelled to
  show another operator's identity. Receipts without `operator_fingerprint`
  now fail. Both the v1 form (128-bit) and the full 256-bit form are
  accepted. Every receipt produced by traceseal and traceseal-observe
  includes a correctly derived fingerprint.

### Added
- Chain-link checks across the receipts given in one run: gaps, forks,
  broken `chain_prev_hash` links, and key changes outside a valid
  dual-signed `chain_key_rotation`. New `check_chains()` API, and
  `--allow-gaps` / `--no-chain` CLI flags.
- Type-aware output for every receipt type (model, tool, data_flow,
  oversight, policy_decision, incident, erasure, …).
  `VerifyResult.receipt_type`, `.summary` and `.receipt_hash`.
- `--json` output includes `chains` when chained receipts are present.
  Without chained receipts the output keeps its original list shape.
- Conformance vectors generated by traceseal-observe 1.5.0, including a
  relabelled-fingerprint attack.
- RECEIPT-SPEC.md synced with the canonical copy in traceseal-observe.

## [1.0.1] — 2026-05-03

### Fixed
- `verify_receipt()` now correctly accepts an empty `provenance: {}` dictionary, conforming to RECEIPT-SPEC.md §2.3 which states all provenance fields are OPTIONAL. Previously, the `not provenance` check rejected empty-dict provenance, causing valid model-call and tool-call receipts (which legitimately have sparse provenance) to fail verification. Caught by conformance test vector `02-valid-model-call`.

### Notes
- This fix is conservative: any receipt that verified under v1.0.0 will still verify under v1.0.1. The change only allows previously-rejected-but-actually-valid receipts to pass, never the reverse.
- No spec changes. No API changes. Drop-in upgrade.

## [1.0.0] — 2026-04-XX

### Added
- Initial public release of the standalone Receipt Verifier.
- Implements RECEIPT-SPEC.md v1.0 §3 (canonical JSON) and §4 (verification algorithm).
- One-command CLI: `traceseal-verify receipt.json`.
- One dependency: `cryptography>=41.0`.
